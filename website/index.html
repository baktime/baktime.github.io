How it works

Encrypted before upload

restic encrypts each snapshot before it reaches your storage. The password stays in your GitHub secrets. Keep a second copy in your password manager for restores.

Less data to transfer

GitHub Actions streams database dumps into restic. For files, restic runs on your Linux host over SSH. It reuses blocks already in storage, so later backups only upload new data.

A message after the run

Send backup results and a weekly report to Discord. Prefer email? GitHub Actions can email you the outcome of workflows you trigger.

Your first backup

Start with one database or directory. The examples use a private GitHub repository and a Cloudflare R2 bucket.

Full configuration reference
  1. Create your private repository

    Open the GitHub template, select your account, name the repository my-backups and choose Private. The repository holds workflows and run history. Backup data goes to your storage.

  2. Connect your backup storage

    Create a private Cloudflare R2 Standard bucket named my-backups. Create an R2 API token with Object Read & Write access to this bucket. In the existing .baktimerc.yml, update the fields below. Substitute your GitHub account, repository, Cloudflare account ID and bucket name. Keep the existing retention settings. 

    owner: example-org
repo: my-backups
restic:
  backend: r2
  repository: s3:https://ACCOUNT_ID.r2.cloudflarestorage.com/my-backups
  passwordSecretName: RESTIC_PASSWORD
  accessKeyIdSecretName: R2_ACCESS_KEY_ID
  secretAccessKeySecretName: R2_SECRET_ACCESS_KEY

    In your repository, open Settings → Secrets and variables → Actions → New repository secret. Add these three secrets separately.

    R2_ACCESS_KEY_ID · R2_SECRET_ACCESS_KEY
    The access key ID and secret access key from the R2 token.
    RESTIC_PASSWORD
    Generate a unique encryption password, for example with openssl rand -base64 32. Save it outside GitHub as well. You need it to read any snapshot.
  3. Choose a database or directory

    PostgreSQL example. Add SHOP_DB_USER and SHOP_DB_PASSWORD as repository secrets for a database user with permission to read the data. Create one more secret named BAKTIME_TARGET_SHOP. Paste the JSON below as its value, replacing the host and database. The example backs up shop at 02:00 UTC every day. 

    {
  "type": "postgres",
  "database": "shop",
  "connection": {
    "mode": "direct",
    "host": "db.example.com",
    "port": 5432
  },
  "userSecretName": "SHOP_DB_USER",
  "passwordSecretName": "SHOP_DB_PASSWORD",
  "schedule": "0 2 * * *"
}

    The runner needs network access to the database. For a private network, use the SSH tunnel example in the configuration reference.

    Linux files example. To copy /srv/uploads at 03:00 UTC, put the SSH private key in UPLOADS_SSH_KEY. Authorize its public key for the backup user on the host. Save this JSON as BAKTIME_TARGET_UPLOADS and replace the host, user and path. 

    {
  "type": "files",
  "host": "files.example.com",
  "sshUser": "backup",
  "sshKeySecretName": "UPLOADS_SSH_KEY",
  "paths": ["/srv/uploads"],
  "schedule": "0 3 * * *"
}
  4. Run once and check the snapshot

    Commit the configuration to main. Open Actions → Backup → Run workflow. A new target is due immediately. Later manual runs pick up only targets due since their last run.

    For the database example, open history/shop.yml. Find status: success and the snapshotId. With restic pointed at the same bucket and credentials, list the snapshots below. Test a restore into a disposable database using the restore guide. A database restore overwrites the selected destination. 

    restic snapshots --tag shop
  5. Turn on the schedule

    For automatic runs, create a Workers KV namespace called BAKTIME_SCHEDULES in Cloudflare. In cloudflare-worker/wrangler.toml, put its ID in the existing [[kv_namespaces]] block. Set GITHUB_OWNER and GITHUB_REPO to the owner and name of your private repository.

    Add three Actions secrets: CLOUDFLARE_ACCOUNT_ID, CLOUDFLARE_API_TOKEN (permission to deploy Workers and write to KV) and GH_PAT (a fine-grained GitHub token for this repository only, with Contents: Read and write).

    Commit the Worker settings to main. In Actions, wait for Deploy Cloudflare Worker to succeed, then run Sync Cloudflare schedule manifest. The Worker checks every five minutes and asks GitHub Actions to run due backups.

  6. Choose where you get notified

    Discord. In your Discord channel, open Integrations → Webhooks and create a webhook. Add the repository secret NOTIFICATION_DISCORD with the value true and paste the webhook URL into NOTIFICATION_DISCORD_WEBHOOK_URL. Run Weekly backup summary from Actions to send a test report.

    Email or GitHub. To receive results for workflows you trigger, select Email or On GitHub under System → Actions in your GitHub notification settings. You can limit these messages to failed workflows.

Can I run it for free?

The template is free. A private instance can run at no cost while its Actions minutes, Worker and KV usage, and R2 Standard storage and operations fit your plans’ allowances.

The default schedule sync runs every 15 minutes, even with one daily backup. To use fewer runner minutes, change the cron in .github/workflows/sync-cloudflare-schedule.yml to 17 * * * * for hourly sync. Run sync manually after editing a target to apply the change immediately. The Worker still checks due backups every five minutes.
